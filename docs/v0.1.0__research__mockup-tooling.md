## Context

The Designer role operates in a CLI environment (Claude Code) without access to graphical design tools like Figma, Sketch, or browser-based editors. This research evaluates available approaches for producing visual mockups that communicate design intent to the Dev and QA roles.

---

## Approach 1: HTML + CSS Mockups (RECOMMENDED)

**Fidelity:** High
**Effort:** Medium
**Output:** Standalone `.html` files viewable in any browser

Write complete HTML documents with inline or embedded CSS that demonstrate the actual design. These files can be opened directly in a browser, shared via GitHub, or served locally.

**Strengths:**
- Produces pixel-accurate representations of the final design
- CSS from the mockup can be extracted directly into `_sass/` files
- No external tools or dependencies required
- Demonstrates responsive behaviour via media queries
- The mockup IS the implementation prototype -- reduces handoff friction

**Limitations:**
- Cannot preview output from within the CLI itself
- Requires the reviewer to open files in a browser

**Recommendation:** This is the primary mockup approach. Write standalone HTML files under `roles/Issues-FS__Dev__Role__Designer/mockups/` that the Dev and QA roles can open in a browser. Each file should be self-contained (embedded CSS, no external dependencies beyond Google Fonts CDN).

**Example structure:**
```
mockups/
  homepage.html          -- Full homepage with hero, grid, footer
  article-page.html      -- Article reading experience
  brief-page.html        -- Daily brief layout
  components.html         -- Badge, tag, callout, citation components
  dark-mode.html          -- Dark mode variant
  mobile-preview.html     -- Viewport constrained to 375px
```

## Approach 2: ASCII Art Mockups

**Fidelity:** Low
**Effort:** Low
**Output:** Inline in markdown documents

Box-drawing characters (`---`, `|`, `+`, and Unicode `---`, `|`, `+`) create structural wireframes directly in markdown files.

**Strengths:**
- Zero tooling required; works in any text editor or markdown renderer
- Excellent for conveying layout structure and spatial relationships
- Renders in GitHub markdown, terminal, and IDEs
- Fast to iterate

**Limitations:**
- Cannot convey colour, typography, or visual weight
- Proportions are approximate at best
- Complex layouts become unwieldy

**Recommendation:** Use for structural wireframes in proposal documents (as done in this proposal). Not suitable as the primary mockup deliverable.

---

## Approach 3: SVG Generation

**Fidelity:** Medium-High
**Effort:** High
**Output:** `.svg` files viewable in browsers and markdown

Write SVG markup directly (XML-based vector graphics). Can represent shapes, text, colours, and basic layout with precision.

**Strengths:**
- Can represent colour, typography, and spatial relationships
- Renders in browsers, GitHub markdown preview, and image viewers
- Scalable without quality loss

**Limitations:**
- SVG markup is verbose and difficult to write by hand for complex layouts
- No interactivity (hover states, responsive behaviour)
- Slow to author compared to HTML+CSS for web design mockups
- Text rendering in SVG can differ from CSS text rendering

**Recommendation:** Useful for diagrams, icons, and simple component illustrations. Not practical for full-page mockups.

---

## Approach 4: Mermaid Diagrams

**Fidelity:** Low
**Effort:** Low
**Output:** Rendered in GitHub markdown, documentation tools

Mermaid syntax generates flowcharts, sequence diagrams, and basic layouts from text descriptions.

**Strengths:**
- Renders natively in GitHub markdown (no tooling needed)
- Good for information architecture diagrams, navigation flows, and component relationships
- Easy to iterate

**Limitations:**
- Cannot represent visual design (colour palettes, typography, spacing)
- Layout control is minimal; Mermaid controls positioning
- Not designed for UI mockups

**Recommendation:** Use for IA diagrams and navigation flow documentation. Not suitable for visual design mockups.

---

## Approach 5: Figma API

**Fidelity:** High
**Effort:** Very High
**Output:** Figma files accessible via browser

Programmatically create Figma designs using the Figma REST API and plugin API.

**Strengths:**
- Industry-standard design output
- Collaborative and shareable
- Full visual fidelity

**Limitations:**
- Requires Figma account and API token (not available in this environment)
- API is designed for reading/exporting, not for authoring full designs
- Extremely verbose for constructing layouts programmatically
- Adds an external dependency to the workflow

**Recommendation:** Not practical for this project. The overhead of API-based design authoring far exceeds the benefit, especially when HTML+CSS achieves comparable fidelity with direct implementability.

---

## Decision

| Approach | Use Case | Priority |
|----------|----------|----------|
| **HTML + CSS** | Full-page mockups, component demos, responsive previews | **Primary** |
| **ASCII art** | Structural wireframes in proposal/spec documents | **Secondary** |
| **Mermaid** | IA diagrams, navigation flows | **Supplementary** |
| **SVG** | Icon design, small component illustrations | **As needed** |
| **Figma API** | Not recommended | **Excluded** |

The next step is to produce HTML mockups for the homepage, article page, and component library as defined in the design proposal.
