## Executive Summary

Over the course of a single session, the Designer role conducted a three-pass design process for the Journalist website redesign: discovery (4 role interviews), synthesis (cross-referencing findings into consensus themes, tensions, and priorities), and specification (7 concrete proposals). Those proposals were then reviewed by the Architect, Dev, and QA roles, producing targeted feedback on feasibility, implementation strategy, and quality assurance.

The result is clear. The site's content quality far exceeds its presentation quality, and the architecture is sound -- the bottleneck is the unmodified Minima theme. All four interviewed roles agree unanimously that content-type differentiation is the single highest-impact change. The technical foundation (Jekyll collections, rich front matter metadata, GitHub Pages deployment) already supports everything the design proposes. The work is additive: new `_sass/`, `_includes/`, and `_layouts/` files layered on top of Minima, with zero changes to the content files or deployment pipeline.

This document presents the revised proposals incorporating all team feedback, resolves the 7 specification ambiguities the Dev flagged, and provides an updated phased roadmap with QA acceptance criteria. The recommendation is to proceed with Phase 1 immediately -- it is a single, well-scoped PR that delivers visible impact with low structural risk.

## Process Summary

The redesign followed a structured three-pass process:

1. **Discovery (4 interviews):** Journalist (site owner, content workflow), Architect (Jekyll architecture, constraints), Dev (implementation feasibility, code quality), QA (adversarial testing, accessibility, edge cases).
2. **Synthesis:** Cross-referenced all four interviews into 8 consensus themes, 5 tensions with explicit resolutions, and a prioritised list of design opportunities.
3. **Specification (7 proposals):** Visual identity, homepage redesign, content type differentiation, navigation and IA, article reading experience, responsive and mobile design, interactive features -- each with concrete values (hex codes, pixel dimensions, CSS snippets).
4. **Team review (3 reviews):** Architect assessed feasibility and performance; Dev assessed implementation effort and spec gaps; QA assessed testability, accessibility, and edge cases.

All documents are linked in the Appendix below.

## Revised Proposals (Incorporating Feedback)

### Proposal 1: Visual Identity & Branding

**Original proposal:** Define a complete colour palette (11 semantic colours), IBM Plex typography system (3 families, 7 weights), spacing scale (8px base), and dark masthead concept, loaded via Google Fonts CDN.

**Team feedback:**
- *Architect:* Self-host fonts as WOFF2 to eliminate third-party dependency, reduce layout shift, and improve load performance. Subset to Latin characters. Consider dropping IBM Plex Mono in favour of the system monospace stack.
- *Dev:* Define all tokens in a single `_sass/_variables.scss` as CSS custom properties. Minima's SCSS variables (`$brand-color`, etc.) must be explicitly overridden -- CSS custom properties alone will not affect compiled Minima values.
- *QA:* Signal Blue on Paper (`#2563EB` on `#FAFAF8` = 4.6:1) sits at the AA floor. Verify independently; any rendering variance could drop below threshold. Test with CDN blocked for fallback rendering.

**Revised recommendation:**
- Self-host IBM Plex Sans and IBM Plex Serif as WOFF2 files in `assets/fonts/`, subset to Latin. Define `@font-face` in `_sass/_typography.scss` with `font-display: swap`. Remove all Google Fonts `<link>` tags.
- Drop IBM Plex Mono. Use system monospace stack: `"Menlo", "Consolas", "Liberation Mono", monospace`. Code blocks are not frequent enough to justify a third font family.
- All tokens defined in `_sass/_variables.scss` as both CSS custom properties and SCSS variables (for Minima override compatibility).
- Signal Blue contrast acknowledged as borderline. Retained for now -- if Lighthouse audits flag it post-implementation, darken to `#2256D0` (estimated 5.2:1).

**Status:** Revised

### Proposal 2: Homepage Redesign

**Original proposal:** Hero section (most recent article), two-column grid (articles 60% / briefs 40%), three-column "More from the Newsroom," category grid with content counts, all kicking in at 768px.

**Team feedback:**
- *Architect:* Liquid merge-and-sort across all collections is feasible but degrades at 100+ items. Cap "Latest Articles" and "Daily Briefs" at 3 items each. Homepage should be the last item in Phase 2 (after component styles stabilise).
- *Dev:* Confirm which collections merge for the hero. Breakpoint conflict: Proposal 2 says 768px, Proposal 6 says 1024px for desktop. Liquid `concat` filter requires Jekyll 3.9.x (GitHub Pages supports this).
- *QA:* Test zero-content states. Empty collections must not render blank cards. "View all" links must not appear for empty collections. Category counts must be dynamic.

**Revised recommendation:**
- Desktop layout at `>= 1024px` (Proposal 6 breakpoints are authoritative; Proposal 2's 768px reference is corrected).
- Hero merges all five collections. Priority order is not needed -- the most recent by date across all types wins. If that happens to be a correction, so be it; the badge makes the type clear.
- Cap "Latest Articles" at 3 items, "Daily Briefs" at 3 items.
- Empty-state rules: if a collection has zero items, omit its column/card entirely. Category grid shows all five types but displays "0 pieces" for empty ones (the grid is also navigation). "View all" links hidden for empty collections.
- Homepage is the final item built in Phase 2, after all component partials and layouts are stable.

**Status:** Revised

### Proposal 3: Content Type Differentiation

**Original proposal:** Five content types (article, brief, interview, investigation, correction) each receive a distinct accent colour, badge, text-glyph icon, and layout template with type-specific formatting.

**Team feedback:**
- *Architect:* Highest-value proposal. Low risk since each layout is standalone. The Interview Q&A "alternating backgrounds" needs a defined markdown convention before the template can be built.
- *Dev:* Each layout extends a shared `post-base.html`. The badge is an `_includes/badge.html` partial. Confirmed that `page.type` in front matter drives everything. Q&A convention unspecified.
- *QA:* Badge colours highly testable. Unicode icons inconsistent cross-platform -- text glyphs confirmed as the right choice. Left accent borders must be pixel-checked across all five types.

**Revised recommendation:**
- All five layouts and the badge component proceed as specified.
- Text glyphs (`[A]`, `[B]`, `[I]`, `[X]`, `[C]`) are the canonical icon system. Unicode emoji are not used.
- Interview Q&A convention (resolved in Spec Ambiguities section below): use `**Q:**` prefix for questions, standard paragraphs for answers.
- Layouts extend a shared `_layouts/post-base.html` to reduce duplication.

**Status:** Approved as-is (with Q&A convention resolved below)

### Proposal 4: Navigation & Information Architecture

**Original proposal:** Top nav bar in the masthead, category landing pages per collection, breadcrumbs on article pages, clickable topic tags linking to per-topic pages, footer navigation.

**Team feedback:**
- *Architect:* `jekyll-archives` is not on the GitHub Pages plugin whitelist. Per-topic pages require either manual maintenance or GitHub Actions. Use a single `/topics/` page with anchor-linked sections instead.
- *Dev:* Topic tags are clickable in Phase 2, but per-topic pages are Phase 3. Where do tags link in Phase 2? Breadcrumbs use `page.collection` and `page.title`. Category landing pages are markdown files with a `collection` layout.
- *QA:* Active nav state must reflect the current section on every page. Breadcrumbs with 120-character titles must not overflow. Topic filtering needs keyboard accessibility. Collections exceeding 50 items need pagination or "load more."

**Revised recommendation:**
- Phase 2: Topic tags link to a single `/topics/` page with anchor sections per topic (e.g., `/topics/#architecture`). This is a single Liquid-generated page, no plugin required.
- Phase 3: Evaluate whether per-topic pages are warranted by content volume. If so, implement via GitHub Actions build (not `jekyll-archives`). Otherwise, the single `/topics/` page remains.
- Breadcrumbs truncate titles exceeding 60 characters with ellipsis on mobile viewports.
- Collections with 20+ items get a "Show more" toggle (CSS-only, initially collapsed beyond 20). Full pagination deferred until content volume requires it.

**Status:** Revised

---

### Proposal 5: Article Reading Experience

**Original proposal:** 680px centred content column, heading scale, code block and blockquote styling, callout boxes, data tables with responsive wrappers, metadata display, source citation block.

**Team feedback:**
- *Architect:* Well-specified, almost entirely CSS. Callout box crosses the dual-readability line if it requires HTML in content. Implement as a Liquid include.
- *Dev:* No specification for how content authors signal "insert a callout here." Sources partial needs a Liquid loop over `page.sources`. The `word-break: break-all` on URLs needs visual confirmation.
- *QA:* Code blocks with 200+ character lines need overflow testing. Nested blockquotes unspecified. Tables wider than 680px must scroll. Missing `page.sources` must result in no "SOURCES" section at all.

**Revised recommendation:**
- Callout mechanism (resolved below): callouts are layout-driven, inserted via Liquid includes in specific layout templates (e.g., investigation layout's "key findings" callout). Content authors do not insert callouts; they come from front matter fields (`key_findings` for investigations).
- Nested blockquotes: inherit the same left-border style with 8px additional left margin per nesting level. No background nesting -- keep it simple.
- Missing metadata fields: render only what exists. No dangling separators. If `page.sources` is absent or empty, the sources section is omitted entirely.

**Status:** Approved as-is (with callout mechanism resolved below)

---

### Proposal 6: Responsive & Mobile Design

**Original proposal:** Three breakpoints (640px / 1024px), hamburger menu with JS toggle below 640px, mobile typography adjustments, responsive tables with "Scroll" indicator, edge-bleed code blocks.

**Team feedback:**
- *Architect:* The hamburger menu is the most JS-dependent feature. Use CSS-only `<details>/<summary>` for progressive enhancement instead.
- *Dev:* Edge-bleed code blocks (`margin-left: -16px`) assume fixed parent padding. Use `calc(-1 * var(--space-md))` with spacing tokens instead.
- *QA:* Hamburger overlay must trap focus for keyboard/screen-reader users. Touch targets must all be measured at 48px. "Scroll" indicator on tables needs a screen-reader-accessible alternative. Test on notched phones for safe-area clipping.

**Revised recommendation:**
- Hamburger menu implemented as CSS-only `<details>/<summary>` disclosure widget. No JavaScript required. This satisfies progressive enhancement (works with JS disabled) and eliminates focus-trapping complexity for Phase 2. If the interaction feels insufficient after user testing, a JS enhancement can be layered on.
- Edge-bleed code blocks use `calc(-1 * var(--space-md))` for resilient negative margins.
- Table scroll indicator uses both the `::after` pseudo-element ("Scroll" text) and a `aria-label="Scrollable table"` on the wrapper for screen reader support.
- Safe-area padding added: `padding-left: max(var(--space-md), env(safe-area-inset-left))` for notched devices.

**Status:** Revised

---

### Proposal 7: Interactive Features

**Original proposal:** Four features: RSS visibility (Phase 1), topic filtering (Phase 2), client-side search via Lunr.js (Phase 3), dark mode toggle (Phase 3).

**Team feedback:**
- *Architect:* Lunr.js indexing full body text produces 300-500KB JSON at 50 articles. Index title, summary, and topics only. Skip body text.
- *Dev:* Search spec describes both a `/search/` page and an optional overlay -- pick one. `search.json` must handle special-character escaping. RSS visibility is trivial (15 minutes).
- *QA:* Test Lunr.js loading delay on 3G throttle. Dark mode must not flash wrong theme. Topic filtering must update ARIA live regions. RSS Amber badge on dark masthead needs contrast check. All JS features must degrade gracefully with JS disabled.

**Revised recommendation:**
- Lunr.js indexes title, summary, and topics only. Body text excluded. This keeps `search.json` under 50KB.
- Search is a dedicated `/search/` page only. The overlay is dropped from scope entirely. Simpler to build, simpler to test, no risk of interaction conflicts with navigation.
- Dark mode deferred per Architect guidance: do not attempt until all Phase 1 and Phase 2 styles are stable.
- Topic filtering announces filtered count via `aria-live="polite"` region.
- RSS Amber badge (`#D97706`) on Ink background (`#1A1A2E`): contrast ratio is 4.8:1 (passes AA). Verified.
- All JS features tested with JS disabled. Content remains accessible; interactive enhancements simply absent.

**Status:** Revised

## Resolved Spec Ambiguities

The Dev flagged 7 specification ambiguities. The Designer's decisions follow.

### 1. Interview Q&A markup convention

**Ambiguity:** The Interview layout specifies "alternating background for questions vs. answers" but does not define how markdown distinguishes questions from answers.

**Decision:** Questions use a `**Q:**` prefix (bold markdown). Answers are standard paragraphs following the question. The Liquid template detects `<strong>Q:</strong>` at the start of a paragraph and wraps it in a `.question` div; everything else is an `.answer` div. This preserves dual readability -- in GitHub's markdown renderer, the Q&A structure is visually clear via the bold prefix.

### 2. Callout trigger mechanism

**Ambiguity:** The proposal says callouts live in layouts, not content, but does not specify how a content author signals "insert a callout here."

**Decision:** Callouts are not author-triggered. They are layout-driven, rendered from structured front matter fields. The investigation layout reads `page.key_findings` (a list) and renders it as a callout box. The article layout has no callouts by default. If a future content type needs author-triggered callouts, a Liquid include (`{% include callout.html text="..." %}`) can be added to the layout, but this is out of scope for v2.

### 3. Topic page link targets in Phase 2

**Ambiguity:** Topic tags are clickable in Phase 2, but per-topic pages are Phase 3. Where do tags link?

**Decision:** Phase 2 tags link to `/topics/#<topic-slug>`. The `/topics/` page is a single Liquid-generated page with an anchor section per topic, listing all content tagged with that topic. This ships in Phase 2 alongside topic tags. Per-topic pages (individual URLs) are deferred indefinitely unless content volume justifies them.

### 4. Collection merging for hero

**Ambiguity:** Which collections merge for the "most recent" hero on the homepage?

**Decision:** All five collections merge. The most recent item by date across all types is promoted to the hero. The badge makes the content type immediately clear regardless of which type it is. No priority ordering or type filtering.

### 5. Reading time calculation

**Ambiguity:** Is reading time from front matter or calculated?

**Decision:** Calculated via Liquid in the `_includes/metadata.html` partial: `{% assign words = content | number_of_words %}{% assign minutes = words | divided_by: 200 %}`. If the result is 0, display "1 min read". This is not a front matter field -- it is derived automatically and stays accurate as content is edited.

### 6. Mobile breakpoint inconsistency

**Ambiguity:** Proposal 2 references `min-width: 768px` for desktop; Proposal 6 defines desktop as `>= 1024px`.

**Decision:** Proposal 6 breakpoints are authoritative. Mobile: `< 640px`. Tablet: `640px - 1023px`. Desktop: `>= 1024px`. All references to 768px in the original proposals are superseded. The two-column grid (articles/briefs) appears at tablet width (640px+). The full homepage layout (hero + two-column + three-column + category grid) appears at desktop width (1024px+).

### 7. Search overlay vs. dedicated page

**Ambiguity:** The proposal describes both a `/search/` page and an optional inline search overlay on desktop.

**Decision:** Build the `/search/` page only. The overlay is removed from scope. One search interface, one implementation, one test surface. If user feedback indicates an overlay would be valuable, it can be added as a Phase 4 enhancement.

## Revised Implementation Roadmap

### Phase 1 -- Foundation & First PR

**Goal:** Transform the visual impression. Pure SCSS + Liquid includes. No layout overhauls, no JavaScript.

**Scope (every file listed):**

New files:
- `assets/fonts/` -- WOFF2 files for IBM Plex Sans (400, 500, 600, 700) and IBM Plex Serif (400, 600, 700)
- `_sass/_variables.scss` -- all design tokens (colours, spacing, typography as CSS custom properties and SCSS variables)
- `_sass/_typography.scss` -- `@font-face` declarations, heading scale, body text
- `_sass/_masthead.scss` -- dark background masthead with Signal Blue accent
- `_sass/_badge.scss` -- five content-type badge variants
- `_sass/_article.scss` -- content column (680px), code blocks, blockquotes, tables, source citations
- `_sass/_responsive.scss` -- breakpoints at 640px / 1024px, mobile typography adjustments, responsive table and code block wrappers
- `_includes/badge.html` -- renders `page.type` as a colour-coded badge
- `_includes/metadata.html` -- renders date, author, calculated reading time, topic pills
- `_includes/sources.html` -- renders `page.sources` as styled citation block (hidden if absent)
- `_includes/skip-link.html` -- "Skip to content" link as first focusable element

Modified files:
- `assets/css/style.scss` -- import Minima, then import all custom partials
- `_includes/head.html` -- remove Google Fonts links, add font preload for WOFF2
- `_includes/header.html` -- masthead redesign with dark background, nav links, RSS badge
- `_includes/footer.html` -- redesigned footer with RSS link and Signal Blue top border

**Accessibility baseline (Phase 1, not deferred):**
- Skip-to-content link on every page
- Single H1 per page (override Minima's duplicate H1 if present)
- Heading hierarchy: no skipped levels
- Visible focus indicators on all interactive elements
- `<html lang="en">` confirmed present

**Not in Phase 1 (explicitly deferred):**
- Custom `_layouts/*.html` (Phase 2)
- Homepage redesign (Phase 2)
- Category landing pages (Phase 2)
- Any JavaScript (Phase 2/3)

---

### Phase 2 -- Layouts, Navigation, Mobile

**Goal:** Distinct reading experiences per content type. Navigable information architecture. Full responsive treatment.

**Scope:**

Layouts:
- `_layouts/post-base.html` -- shared base (masthead, breadcrumbs, metadata, footer)
- `_layouts/article.html` -- full-width reading, summary as sub-headline, source citations
- `_layouts/brief.html` -- compact, date-prominent, smaller body text (16px)
- `_layouts/interview.html` -- Q&A formatting with `.question`/`.answer` alternating styles
- `_layouts/investigation.html` -- top banner, key findings callout from `page.key_findings`
- `_layouts/correction.html` -- minimal, links to corrected article, dual dates
- `_layouts/collection.html` -- category landing page with card list
- `_layouts/home.html` -- hero + two-column + three-column + category grid

Includes:
- `_includes/breadcrumbs.html` -- Home > Collection > Title (truncated at 60 chars on mobile)
- `_includes/card.html` -- reusable card (badge, title, summary, date, topics)
- `_includes/hero.html` -- featured article hero section
- `_includes/topic-pills.html` -- renders topics as clickable pills linking to `/topics/#slug`
- `_includes/callout.html` -- callout box (used by investigation layout)

Pages:
- `articles.md`, `briefs.md`, `interviews.md`, `investigations.md` -- category landing pages
- `topics.html` -- single topics page with anchor sections per topic
- `about.md` -- About page explaining the site, the Journalist role, and the ecosystem

Navigation:
- Top nav bar with active state indicator
- CSS-only hamburger menu via `<details>/<summary>` below 640px
- Footer navigation with all category links

Responsive:
- Full mobile layout (single-column stacking)
- Tablet layout (two-column where appropriate)
- Safe-area padding for notched devices
- 48px touch targets on all interactive elements

**Sequencing within Phase 2:**
1. SCSS partials for new layouts (`_brief.scss`, `_interview.scss`, etc.)
2. `_includes/` partials (breadcrumbs, card, hero, topic-pills, callout)
3. `_layouts/post-base.html` and the five content-type layouts
4. Category landing pages and `/topics/` page
5. About page
6. `_layouts/home.html` (last -- depends on all component styles being stable)
7. CSS-only hamburger menu

---

### Phase 3 -- Search, Dark Mode, Polish

**Goal:** Enhanced discovery, personalisation, and remaining polish.

**Scope:**

Search:
- `search.json` -- Liquid template indexing title, summary, and topics only (no body text)
- `assets/js/search.js` -- Lunr.js lazy-loaded on first interaction
- `search.md` -- dedicated `/search/` page with input, results, and no-results state
- `_sass/_search.scss` -- search page styles

Dark mode:
- Convert all colour values to CSS custom properties (if not already done in Phase 1)
- `_sass/_dark-mode.scss` -- dark palette overrides
- Inline `<script>` in `<head>` (before stylesheet) to read `localStorage` / `prefers-color-scheme`
- Toggle button in masthead (sun/moon text glyph, 48px touch target)
- Verify all badge colours against dark backgrounds

Polish:
- Print stylesheet (`_sass/_print.scss`) -- no nav, no footer, no backgrounds, readable fonts
- Previous/next navigation within collections (Liquid-only, at article bottom)
- Auto-generated table of contents for articles with 3+ headings
- `prefers-reduced-motion` media query to disable transitions/animations

## Open Questions for Dinis

1. **Brand name "Issues-FS News"** -- the masthead uses this title with the tagline "Journalism from inside the Issues-FS agentic ecosystem." Is this the right name, or would you prefer something different? The name frames reader expectations on every page load.

2. **IBM Plex as the type family** -- the revised recommendation self-hosts IBM Plex Sans and Serif (dropping Mono). IBM Plex is open-source, highly legible, and has a technical-journalism feel. Are you comfortable with this choice, or is there another font family you would prefer? This decision cascades through every element of the design.

3. **Dark mode priority vs. search priority** -- both are Phase 3. If only one can ship in the next sprint, which matters more? Search adds discovery value as the content library grows. Dark mode adds reader comfort and signals design polish. The Designer's instinct is search-first (functional value over aesthetic value), but this is a product decision.

4. **About page content** -- the design includes an About page layout, but the content needs authoring. Should the Journalist role draft the About page content, or would you like to provide direction on what it should say? Key questions: how much should it explain about the agentic ecosystem? Should it name Dinis Cruz as the human behind the project?

5. **Correction policy visibility** -- the current design includes a Correction content type with its own layout. Should there be a standing "Corrections Policy" section on the About page explaining how corrections are handled? This is standard practice for news publications and reinforces editorial credibility.
